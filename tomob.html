tomob

게임에서 재화를 얻고, 그 재화로 실제 프로덕트 제작을 의뢰하는 게임형 제작 플랫폼. 게임 시스템과 외주 제작 경험을 하나의 루프로 연결했어요.

RoleProduct Strategy · System Design · Build
TypeGame-based Product Commission Platform
StackThree.js · Rapier · JavaScript
Year2026

01   Product Idea

Can Play Turn Into Real Products?

게임에서 얻은 성취가 실제 프로덕트 제작으로 이어질 수 있을까?

tomob의 핵심은 게임 자체가 아니었어요. 탐험·전투·항해로 재화를 모으고 그 재화로 디자인·개발 같은 외주 프로덕트를 의뢰하는 경험을 구상했어요. 놀이의 동기와 실제 제작 서비스를 하나의 경제 안에 연결하려는 제품 실험이었어요.

02   Core Loop

Play Ends in a Commission, Not a Reward

플레이가 끝나는 지점을 보상이 아니라 제작 의뢰로 바꿨어요.

게임의 성취를 게임 밖에서 쓸 수 있는 결과물로 넘기는 게 이 제품의 루프예요.

01 · PLAY탐험과 전투월드를 이동하고 전투·항해·채집 활동을 수행해요.
02 · EARN게임 재화 획득플레이 결과로 제작 의뢰에 사용할 수 있는 재화를 축적해요.
03 · COMMISSION프로덕트 의뢰필요한 디자인·개발 작업의 범위와 조건을 선택해요.
04 · BUILD실제 결과물게임 밖에서 사용할 수 있는 실제 프로덕트 제작으로 연결돼요.

04   Evolution

The Tech Changed With the Question

게임의 형태보다, 지금 검증할 게 무엇인지에 따라 기술을 바꿨어요.

tomob는 처음부터 지금 모습이 아니었어요. 탑뷰로 핵심 루프를 확인한 뒤 공간 경험을 위해 Voxel로 전환했고, 프레임·표현의 한계를 확인한 뒤 Mesh 월드로 다시 옮겼어요.

Top ViewVoxel WorldMesh WorldModular BuildHarness Refactor

Phase 02 · Voxel

직접 탐험하고 만드는 감각을 위해 Voxel 월드로 전환했어요.

1인칭 공간, 블록 지형, Seed 월드, 제작·항해를 한 환경에 넣었어요. 범위는 빠르게 넓어졌지만 블록 수가 늘수록 프레임 비용과 장면 관리 복잡도가 함께 커졌어요.

섬의 역할·항로를 먼저 정의한 월드맵 구상(좌) → 게임 내 탐색 지도로 옮긴 구현(우)

Phase 03 · Mesh

프레임·표현의 한계를 해결하려고 Mesh 기반 월드로 업그레이드했어요.

Voxel을 끝까지 최적화하는 대신, 이미 만들어진 3D 에셋과 Mesh 지형을 쓰는 방향으로 기술 선택을 바꿨어요. 한 화면에 더 많은 시스템을 올리면서도 인트로·전투·항해의 연출 밀도를 높일 수 있었어요.

Phase 04 · Modular

기능을 모듈로 분리하면서 병렬 개발이 가능해졌어요.

전투·항해·스킬·크루·세이브를 각 모듈로 나누고 공통 컨텍스트로 연결했어요. 독립적인 기능은 동시에, 의존성 있는 작업만 순서대로 이어갔어요.

전투 · 항해 · 스킬 · 항해전투를 독립 모듈로 분리한 뒤 공통 컨텍스트로 연결

05   Product System

Systems Behind the Screen

게임 화면 뒤에는 서로 영향을 주는 시스템이 있었어요.

Phase 05 · Harness — 병렬 개발은 속도를 높였지만 모듈 사이 회귀 버그도 늘렸어요. 문법 검사로 안 잡히는 입력 충돌·세이브 복원·물리 상태·보상·밸런스를 자동 Check와 시뮬레이션 불변식으로 검증했어요.

06   Key Decision

Structure That Catches AI's Mistakes

프롬프트를 잘 쓰는 것보다, AI가 틀려도 발견되는 구조가 필요했어요.

작업이 커질수록 긴 지시문보다 단일 진실 공급원, 명시적 모듈 경계, 자동 검증이 더 중요했어요. 새 입력은 입력 라우터로, 새 이벤트는 이벤트 시스템으로, 새 밸런스 값은 BAL로 들어가게 규칙을 고정했어요.

01작업 범위 정의한 번에 건드릴 파일과 건드리지 않을 파일을 먼저 적어요. 범위가 넓으면 뭐가 깨졌는지 못 찾아요.
02SSOT 확인밸런스 수치는 BAL, 키 바인딩은 키맵 문서. 값이 두 곳에 생기려 하면 그 자리에서 막아요.
03작은 단위 구현기능 하나씩 넣고 바로 돌려봐요. 여러 개를 한꺼번에 넣으면 원인 추적이 불가능해져요.
04자동 Check부팅·키 충돌·세이브 복원·보상 불변식을 스크립트가 검사해요. 사람 눈으로 안 잡히는 회귀를 여기서 걸러요.
05실플레이 판정자동 검사를 통과해도 손맛은 직접 해봐야 알아요. 통과와 재미는 다른 판정이에요.

문장으로 반복 설명하는 대신, 실제 화면에서 움직이며 확정하는 도구를 직접 만들었어요.

08   Verification

A Harness, Not a Gut Feel

AI가 만든 버그를 감으로 찾지 않도록 검사 하네스를 만들었어요.

문법 검사만으로는 물리·상태 버그를 못 찾았어요. 부팅·키 충돌·아이템·세이브·밸런스·몹·퀘스트를 자동 검사하고, 장시간 시뮬레이션으로 배 보상·항구 상태 같은 불변식을 확인했어요.

Case 01

Rapier 이중 제거

같은 rigid body를 두 번 제거해 나던 크래시를 수명주기 규칙으로 차단.

Case 02

공유 머티리얼

복제 몬스터가 머티리얼을 공유해 피격 상태가 번지던 문제를 개별 복제로 해결.

Case 03

백그라운드 렌더

숨겨진 탭의 rAF 정지가 만든 가짜 VFX 결과를 발견, 검증 방법을 분리.

tomob를 만들며 배운 건 AI가 코드를 얼마나 많이 쓰는가보다, 복잡한 작업을 어떤 구조로 통제하는가였어요.
